# 3.4.0 Presence Transport Spike

## Status

Feasibility instrumentation added for controller-run two-user proof. Results
and observations are pending controller measurement.

## Purpose And Boundary

This spike proves that ephemeral presence can ride a transport separate from
Replicache. Presence covers who-is-here roster state plus cursor and typing
signals. It is temporary, development-only instrumentation that chooses and
proves the transport for 3.4.3 Live Presence.

This phase does not ship production presence UI. The board view is 3.4.1, and
the production live-presence surface is 3.4.3.

## Transport Options Considered

### Supabase Realtime Presence + Broadcast on a separate channel - chosen

Use Supabase Realtime Presence for the who-is-here roster and Broadcast for
cursor/typing events on `tidy:presence:<roomId>`.

This matches the existing Realtime infrastructure already used for private
per-user pokes while keeping presence off the structural sync lane. It also
keeps the spike small: authenticated socket setup, private channel config, and
bounded in-memory event capture can be proven without adding a new service.

### Dedicated standalone WebSocket service

A standalone service could give tighter control over rate limits, coalescing,
and room authorization, but it adds deployment and operational surface before
there is evidence the existing Realtime stack cannot handle the initial
presence use case.

### Coupling presence into Replicache push/pull - rejected

Replicache is the structural sync spine for lists, items, and the future board.
Presence is ephemeral and high-frequency. Coupling it into push/pull would
violate the 3.0 collaboration arc invariant that structural sync and ephemeral
presence ride separate transports.

## Separation Invariant

Presence does not touch Replicache push/pull, `server-apply`, `/api/replicache/*`,
tRPC dashboard mutations, persisted data, CVR state, or replicated entity
fields. The spike stores only bounded in-memory roster and event state in the
browser.

## Gate And Development API

The gate is off unless all of these conditions hold:

- The build is not production.
- Browser local storage is available.
- `tidy:presence-spike` equals `1` before the dashboard provider mounts.

Enable it separately in each browser profile from DevTools, then reload:

```js
localStorage.setItem("tidy:presence-spike", "1");
location.reload();
```

After reload, `window.__tidyPresenceSpike` exposes:

- `join(roomId)` - authenticates the Realtime socket and joins
  `tidy:presence:<roomId>`.
- `updateCursor(x, y)` - tracks local cursor coordinates and broadcasts the
  latest cursor payload.
- `setTyping(bool)` - tracks local typing state and broadcasts the latest
  typing payload.
- `roster()` - returns the deduped who-is-here roster.
- `events()` - returns the bounded in-memory cursor/typing event buffer.
- `leave()` - removes the channel and clears local spike state.

Disable the spike and reload both profiles after measurement:

```js
localStorage.removeItem("tidy:presence-spike");
location.reload();
```

## Feasibility Proof Protocol

Use two authenticated browser profiles on the same machine. Use two users that
can access the same target board/list context, and choose one shared room id
such as `board-<listId>` or another explicit test room id recorded below.

1. Enable `tidy:presence-spike=1` in both profiles and reload both dashboards.
2. In profile A, run:

   ```js
   await window.__tidyPresenceSpike.join("presence-proof-room");
   ```

3. In profile B, run the same join command with the same room id.
4. In both profiles, inspect:

   ```js
   window.__tidyPresenceSpike.roster();
   ```

   Each profile should show the peer in the who-is-here roster after Realtime
   sync.

5. In profile A, run:

   ```js
   window.__tidyPresenceSpike.updateCursor(100, 200);
   window.__tidyPresenceSpike.setTyping(true);
   ```

6. In profile B, inspect:

   ```js
   window.__tidyPresenceSpike.events();
   ```

   The peer should receive bounded cursor/typing Broadcast events.

7. In profile A, run:

   ```js
   window.__tidyPresenceSpike.leave();
   ```

8. In profile B, inspect `roster()` again and confirm the peer leaves after
   Realtime emits the presence update.

## Limitations And Open Questions

- Realtime RLS/auth behavior for `tidy:presence:<roomId>` still needs the
  controller-run proof against the active Supabase policies.
- Cursor and typing Broadcast rate limits, client-side coalescing, and payload
  cadence are intentionally not solved in this spike.
- The production room-key strategy is still open. 3.4.3 must decide whether
  rooms key by board id, list id, workspace id, or a composed permission-scoped
  identifier.
- This spike does not render cursors, typing indicators, or a who-is-here UI.

## What 3.4.3 Inherits

3.4.3 should inherit the separate transport decision, the private
`tidy:presence:<roomId>` namespace, Presence for roster state, Broadcast for
cursor/typing events, production auth/RLS requirements, and the need for
client-side coalescing before any high-frequency cursor UI ships.

## Removal Steps

remove:

2. `lib/realtime/presence-topic.ts` if the production transport does not reuse

4. The `installPresenceSpikeWindowApi` import and `useEffect` mount in
   `components/ReplicacheProvider.tsx`.

Keep this report and the `docs/DECISIONS.md` entry as the durable record.
