# 3.1.0 Sync Latency Measurement Spike

## Status

Measurement status: **pending controller measurement**.

This document defines the measurement procedure and report shape. No real run
data was supplied during implementation, so the result tables, bottleneck
hypothesis, and 3.1.1 scope remain intentionally incomplete. Phase 3.1.0 cannot
be considered complete until real results are recorded here.

## Purpose And Boundary

Measure the existing Replicache path from a local dashboard mutation through
push, Supabase Broadcast poke, peer pull, and peer-visible render under
representative load. This spike does not change sync behavior or implement a
latency fix. Phase 3.1.1 must be scoped from the measurements rather than from
an assumed bottleneck.

The instrumentation is temporary, disabled by default, development-only, and
stores events in memory. It does not add fields to replicated data, alter wire
contracts, or record mutation payloads or user-entered text.

## Instrumented Stages

| Stage | Context | Meaning |
| --- | --- | --- |
| `local_mutation` | origin | Dashboard mutator method was invoked. |
| `push_start` | origin | The Replicache pusher began its HTTP operation. |
| `push_complete` | origin | The push returned a successful HTTP status. |
| `push_failure` | origin | The push threw or returned an error HTTP status. |
| `poke_received` | peer | The private Broadcast callback ran. |
| `pull_start` | peer | The Replicache puller began its HTTP operation. |
| `pull_complete` | peer | The pull returned a successful HTTP status. |
| `pull_failure` | peer | The pull threw or returned an error HTTP status. |
| `peer_render` | peer | The generated trial marker first appeared in the DOM. |

Each event includes a browser-session ID, manually shared trial ID, epoch
milliseconds for same-machine cross-context comparison, monotonic milliseconds
for within-context intervals, and limited safe metadata such as mutation name,
entity ID, request ID, counts, and HTTP status.

## Gate And Development API

The gate is off unless all of these conditions hold:

- The build is not production.
- Browser local storage is available.
- `tidy:sync-latency-spike` equals `1` before the page loads.

Enable it separately in each measurement profile from browser DevTools, then
reload:

```js
localStorage.setItem("tidy:sync-latency-spike", "1");
location.reload();
```

After reload, `window.__tidySyncLatency` exposes only:

- `startTrial(trialId)` - activates a shared trial and returns its generated
  marker.
- `stopTrial()` - stops the current trial and render observer.
- `events()` - returns a copy of buffered events.
- `clear()` - clears the bounded in-memory buffer.
- `exportJson()` - exports buffered events as formatted JSON.

Disable the spike and reload both profiles after measurement:

```js
localStorage.removeItem("tidy:sync-latency-spike");
location.reload();
```

The disabled mutation hook returns Replicache's original mutator object, and
all event functions are no-ops.

Use two authenticated browser profiles on the same machine. Use an owner in the

the same shared list. Same-machine execution keeps the two `Date.now()` clocks
comparable without introducing device clock skew. Use a disposable workspace;

render timing. Record whether DevTools was open and keep that choice consistent
for every scenario.

## Trial Procedure

1. Enable the gate in both profiles and reload both dashboards.
2. Prepare the scenario's workspace size, then wait until both profiles show the
   same state and network activity is idle.
3. Run five warm-up trials. Discard them from reported percentiles.
4. Before each measured mutation, clear both event buffers.
5. Choose a unique trial ID such as `baseline-001`.
6. In the peer profile first, start the trial and retain the returned marker:

   ```js
   window.__tidySyncLatency?.clear();
   window.__tidySyncLatency?.startTrial("baseline-001");
   ```

7. Start the same trial ID in the origin profile. The returned marker must match
   the peer marker.
8. In the origin UI, rename the selected shared list to the returned marker.
   The marker is generated instrumentation text, not user content.
9. Wait for the peer profile to display the marker. Do not manually refresh.
10. Stop the trial in both profiles and export each event buffer:

    ```js
    window.__tidySyncLatency?.stopTrial();
    copy(window.__tidySyncLatency?.exportJson());
    ```

11. Store the two JSON exports under the trial ID outside the repository until
    aggregate results are calculated. Raw run logs may contain internal entity
    IDs and should not be committed.
12. Repeat until there are at least 30 valid post-warm-up samples per scenario.
    Count failed or incomplete trials; do not silently discard them.

If a trial has no `poke_received` but later renders after a periodic pull, mark
it as a missed-poke/self-heal observation. Do not combine it with poke-path
percentiles.

## Metric Calculation

For each valid trial, join origin and peer events by `trialId`.

| Metric | Calculation |
| --- | --- |
| Local-to-push | origin `push_start.wallClockMs` - origin `local_mutation.wallClockMs` |
| Push duration | origin `push_complete.monotonicMs` - origin `push_start.monotonicMs` |
| Push-to-poke | peer `poke_received.wallClockMs` - origin `push_complete.wallClockMs` |
| Poke-to-pull | peer `pull_start.monotonicMs` - peer `poke_received.monotonicMs` |
| Pull duration | peer `pull_complete.monotonicMs` - peer `pull_start.monotonicMs` |
| Pull-to-render | peer `peer_render.monotonicMs` - peer `pull_start.monotonicMs` |
| Pull-complete-to-render | peer `peer_render.monotonicMs` - peer `pull_complete.monotonicMs` |
| End-to-end | peer `peer_render.wallClockMs` - origin `local_mutation.wallClockMs` |

Calculate p50 and p95 with nearest ranks `ceil(0.50 * sampleCount)` and
`ceil(0.95 * sampleCount)`. Also report maximum, valid sample count, failure
count, and observed outliers for every metric. Preserve the same calculation
method for the 3.1.1 before/after comparison.

## Measurement Limitations

- Epoch timestamps are comparable only because both profiles run on one
  machine. Do not use this protocol across unsynchronized devices.
- `local_mutation` is the call into the Replicache mutator surface, not the
  physical pointer event that initiated it.
- `pull_complete` marks completion of the puller's HTTP operation. Replicache
  still has to apply the patch and notify subscribers afterward; `peer_render`
  captures the user-visible end of that remaining interval.
- `peer_render` observes the generated marker's first appearance in DOM text.
  It deliberately limits the measured mutation to a visible rename and does not
  generalize to non-text state changes.
- Replicache can coalesce mutations into one push. `mutationCount` identifies
  that condition, but individual push duration cannot then be attributed to one
  mutation.
- Periodic pulls can occur while a trial is active. Use stage ordering relative
  to `poke_received` and classify trials without a poke separately.
- Browser scheduling, DevTools, background throttling, network variability, and
  external Supabase/Postgres load remain sources of variance.

## Instrumentation Removal

After the report contains accepted measurements, remove or explicitly retain
the gate before closing the spike. Full removal consists of:

1. Remove `lib/sync/sync-latency-spike.ts`.
2. Restore `hooks/useDashboardMutations.ts` to return `rep.mutate` directly.
3. Remove the measured pusher/puller wrappers from
   `lib/sync/replicache/client.ts`; retain the existing correction behavior.
4. Remove poke recording and the development API lifecycle from
   `components/ReplicacheProvider.tsx`.
5. Remove `tests/unit/sync-latency-spike.test.ts`.
6. Keep this report as the durable evidence for 3.1.1.

If the instrumentation remains temporarily gated for the 3.1.1 before/after
comparison, record that decision here and remove it when 3.1.1 closes.
